Các API notification này phục vụ 2 phần: xem lịch sử thông báo đã lưu trong DB và cập nhật trạng thái đã đọc.
GET /api/v1/notifications
Lấy danh sách thông báo của user đang đăng nhập. API này chỉ trả notification thuộc về chính user đó.
Có thể filter/sort/phân trang bằng query params:
keyword=java
type=JOB_APPLICATION_CREATED
read=false
fromDate=2026-05-01T00:00:00
toDate=2026-05-24T23:59:59
pageNum=1
pageSize=10
sortBy=createdAt
isAscending=false
Dùng cho màn hình “Notifications” hoặc dropdown notification.
GET /api/v1/notifications/unread-count
Trả về số lượng notification chưa đọc của current user.
Ví dụ response data:
{
  "unreadCount": 5
}
Dùng để hiển thị badge đỏ trên icon chuông.
PUT /api/v1/notifications/{id}/read
Đánh dấu một notification là đã đọc.
Chỉ owner của notification mới được phép gọi. Nếu user A cố mark notification của user B thì sẽ bị 404 hoặc 403 theo convention hiện tại.
Dùng khi user click vào một notification cụ thể.
PUT /api/v1/notifications/read-all
Đánh dấu toàn bộ notification chưa đọc của current user thành đã đọc.
Dùng cho nút “Mark all as read”.
DELETE /api/v1/notifications/{id}
Soft delete/hide một notification khỏi danh sách của current user. Không xóa cứng DB, chỉ set deleted = true.
Dùng nếu frontend muốn có nút xóa/ẩn từng thông báo.
WebSocket thì không phải REST API, nhưng liên quan trực tiếp:
/ws?token=<access_token>
Frontend connect WebSocket tới endpoint này. Sau đó subscribe:
/user/queue/notifications
Khi backend tạo notification mới, nó sẽ:
1.
Lưu notification vào tbl_notifications
2.
Push realtime cho đúng user đang online qua /user/queue/notifications
Ví dụ flow thực tế:
Candidate apply job thành công:
•
Backend tạo notification cho recruiter.
•
Recruiter nếu đang online sẽ nhận realtime qua WebSocket.
•
Notification cũng được lưu DB.
•
Recruiter reload trang vẫn thấy notification qua GET /api/v1/notifications.

Trong feature notification thì các API REST chính chỉ có 5 API này:
GET    /api/v1/notifications
GET    /api/v1/notifications/unread-count
PUT    /api/v1/notifications/{id}/read
PUT    /api/v1/notifications/read-all
DELETE /api/v1/notifications/{id}
Ngoài REST API, còn có WebSocket endpoint:
/ws
và client subscribe:
/user/queue/notifications
Không có API tạo notification public cho frontend gọi trực tiếp. Notification được tạo tự động từ các business flow hiện có:
POST /api/v1/job/{jobId}/apply
Khi candidate apply job thành công, recruiter/owner job nhận notification.
PUT /api/v1/applications/{applicationId}/status
Khi recruiter/admin đổi trạng thái đơn ứng tuyển, candidate nhận notification.
POST /api/v1/recruiter/tests/{testId}/assign
Khi recruiter assign assessment test, candidate nhận notification.
POST /api/v1/candidate/test-assignments/{assignmentId}/submit
Hoặc endpoint submit test tương ứng trong CandidateAssessmentController, khi candidate nộp bài, recruiter nhận notification.
PATCH /api/v1/companies/{id}/approve
PATCH /api/v1/companies/{id}/reject
Khi admin approve/reject company, owner/recruiter của company nhận notification.
Về ATS screening: mình đã thêm event/listener AtsScreeningCompletedEvent, nhưng trong code hiện tại không có service ATS Java để publish event, nên chưa có API ATS cụ thể được nối vào notification. Khi module ATS có endpoint screening thật, chỉ cần publish event sau khi screening hoàn tất

Bạn test theo 3 lớp: REST lưu DB đúng, WebSocket realtime đúng, và business event tự tạo notification đúng.
1. Chuẩn Bị
Chạy backend:
mvn spring-boot:run
Cần có ít nhất:
1 candidate account
1 recruiter account
1 admin account
1 company của recruiter
1 job published của recruiter
1 assessment test published
Login từng user để lấy token:
POST /api/v1/auth/login
Lưu lại:
candidate_token
recruiter_token
admin_token
2. Test REST Notification Trước
Dùng token recruiter hoặc candidate gọi:
GET /api/v1/notifications
Authorization: Bearer <token>
Kỳ vọng:
200 OK
data.items là danh sách notification của chính user đó
Test unread count:
GET /api/v1/notifications/unread-count
Authorization: Bearer <token>
Kỳ vọng:
{
  "status": "SUCCESS",
  "data": {
    "unreadCount": 0
  }
}
Nếu chưa có notification thì count có thể là 0, bình thường.
3. Test WebSocket Realtime
Mở frontend test bằng Postman WebSocket không phù hợp lắm vì đây là STOMP + SockJS. Dễ nhất là tạo file HTML nhỏ hoặc dùng script frontend.
Bạn có thể dùng ví dụ trong:
docs/notification-websocket-guide.md
Frontend connect:
http://localhost:8080/ws?token=<recruiter_token>
Subscribe:
/user/queue/notifications
Kỳ vọng:
Connect thành công, không bị 401.
4. Test Flow Candidate Apply Job
Mở WebSocket bằng recruiter_token.
Sau đó candidate gọi:
POST /api/v1/job/{jobId}/apply
Authorization: Bearer <candidate_token>
Content-Type: application/json
Body ví dụ:
{
  "coverLetter": "I am interested in this job"
}
Kỳ vọng realtime recruiter nhận được notification:
{
  "type": "JOB_APPLICATION_CREATED",
  "title": "New job application",
  "content": "... has applied for ...",
  "targetType": "APPLICATION",
  "read": false
}
Sau đó recruiter gọi:
GET /api/v1/notifications
Authorization: Bearer <recruiter_token>
Kỳ vọng notification vừa nhận cũng có trong DB.
5. Test Mark Read
Lấy id notification vừa tạo, gọi:
PUT /api/v1/notifications/{id}/read
Authorization: Bearer <recruiter_token>
Kỳ vọng:
"read": true
Gọi tiếp:
GET /api/v1/notifications/unread-count
Authorization: Bearer <recruiter_token>
Kỳ vọng count giảm đi 1.
6. Test Không Được Đọc Notification Người Khác
Dùng candidate_token mark read notification của recruiter:
PUT /api/v1/notifications/{recruiterNotificationId}/read
Authorization: Bearer <candidate_token>
Kỳ vọng:
404 hoặc 403
Miễn là không cho update là đúng.
7. Test Update Application Status
Mở WebSocket bằng candidate_token.
Recruiter gọi:
PUT /api/v1/applications/{applicationId}/status
Authorization: Bearer <recruiter_token>
Content-Type: application/json
Body:
{
  "status": "APPROVED",
  "reviewNote": "Good profile"
}
Kỳ vọng candidate nhận realtime:
{
  "type": "JOB_APPLICATION_STATUS_UPDATED",
  "title": "Application status updated",
  "content": "Your application for ... has been updated to APPROVED",
  "targetType": "APPLICATION"
}
8. Test Assessment Assigned
Mở WebSocket bằng candidate_token.
Recruiter gọi:
POST /api/v1/recruiter/tests/{testId}/assign
Authorization: Bearer <recruiter_token>
Content-Type: application/json
Body:
{
  "applicationIds": [1]
}
Kỳ vọng candidate nhận:
{
  "type": "ASSESSMENT_ASSIGNED",
  "title": "Assessment assigned"
}
9. Test Candidate Submit Assessment
Mở WebSocket bằng recruiter_token.
Candidate submit test theo API candidate assessment hiện có.
Kỳ vọng recruiter nhận:
{
  "type": "ASSESSMENT_SUBMITTED",
  "title": "Assessment submitted"
}
10. Test Company Approve/Reject
Mở WebSocket bằng token của company owner/recruiter.
Admin gọi:
PATCH /api/v1/companies/{companyId}/approve
Authorization: Bearer <admin_token>
hoặc:
PATCH /api/v1/companies/{companyId}/reject
Authorization: Bearer <admin_token>
Kỳ vọng owner/recruiter nhận:
{
  "type": "COMPANY_APPROVED"
}
hoặc:
{
  "type": "COMPANY_REJECTED"
}
